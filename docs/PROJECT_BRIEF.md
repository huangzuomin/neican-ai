# neican.ai Knowledge Engine 项目说明

## 0. 最终版项目目标

neican.ai 项目的目标，是建设一个基于 OpenClaw 的 AI 行业知识生产引擎。

它不是传统资讯站，也不是自动发文系统，而是一个将 AI 行业信息转化为结构化知识资产的智能工作区。

系统以事件为核心，把外部资讯经过采集、清洗、去重、事件建模、实体归档、主题归档、声明抽取和编辑决策后，沉淀到 Memory Wiki，并按价值等级输出为日报、洞察文章、实体页、主题页、概念页和时间线。

第一阶段只追求跑通最小闭环：OpenClaw 子智能体工作区、低权限沙箱抓取、SQLite 运行账本、Memory Wiki 知识资产、Hugo 静态发布和 Codex 编码施工。

项目不以内容数量为目标，而以信息判断质量、知识沉淀能力、发布可控性和长期复用价值为目标。

## 1. 项目定位

本项目用于重构 `neican.ai`，使其从一个“自动化 AI 资讯发布网站”，升级为一个基于 OpenClaw 的 AI 行业知识生产引擎。

系统目标不是：

```text
抓一条资讯 → 写一篇文章 → 发到网站
```

而是：

```text
采集资讯 → 沙箱清洗 → 去重入库 → 事件建模 → 编辑决策 → 更新 Memory Wiki → 生成文章/日报/知识资产 → 导出 Hugo → 发布网站
```

核心资产不再是单篇文章，而是持续生长的：

```text
事件索引
实体档案
主题知识页
概念词条
结构化声明 Claims
日报/周报
洞察文章
时间线
综合报告
```

neican.ai 的最终定位是：

> 基于 OpenClaw 的 AI 行业情报索引、结构化知识网络与自动化内容生产系统。

---

## 2. 第一阶段 MVP 目标

第一阶段只做最小可行闭环，目标是让系统能够稳定运行，而不是追求完整知识图谱或复杂后台。

MVP 需要完成：

1. 从配置文件读取精选 AI 行业信源。
2. 支持 RSS 抓取和基础网页内容入库。
3. 使用 SQLite 进行 hash 去重和运行记录。
4. 将原始资讯建模为事件 Event。
5. 对事件进行实体、主题、声明、价值评分抽取。
6. 根据编辑规则做 A/B/C/D 分级决策。
7. A 级事件生成独立文章草稿。
8. B/C 级事件进入日报或仅更新知识资产。
9. D 级事件忽略或只记录。
10. 支持生成 Hugo Markdown 和标准 Front Matter。
11. 支持本地 Hugo build 校验。
12. 关键节点支持人工审核队列。
13. 运行过程可审计、可回滚、可追踪。

第一阶段禁止引入或实现以下内容：


## 4. 核心技术栈

第一阶段采用：

```text
OpenClaw：唯一智能中枢和运行时
OpenClaw Gateway：对话控制台与审核入口
OpenClaw Cron：定时采集与日报触发
OpenClaw Skills：稳定工艺封装
OpenClaw llm-task：结构化 LLM 输出
OpenClaw Lobster：关键审批和发布流程
OpenClaw Memory Wiki：知识资产层
SQLite：运行账本
Hugo：静态页面生成器
Git：版本控制与回滚
Python：脚本和工具实现
```

---

## 5. 角色分工

### OpenClaw

负责：

- 调度任务。
- 执行 Skills。
- 调用 LLM 做结构化判断。
- 维护 Memory Wiki。
- 触发审核。
- 生成草稿。
- 组织发布流程。

### SQLite

负责：

- 原始资讯记录。
- 事件索引。
- 编辑决策。
- 审核队列。
- 发布日志。
- 运行日志。

SQLite 不是 CMS，不存长期知识正文。

### Memory Wiki

负责：

- 长期知识资产。
- 实体页。
- 概念页。
- 主题页。
- 时间线。
- 综合报告。
- 草稿。
- 结构化声明 Claims。

### Hugo

负责：

- 公开网站静态页面生成。
- 渲染 Markdown。
- 生成 sitemap/RSS。
- 输出 SEO 页面。

Hugo 不参与编辑决策，也不作为知识源头。

---

## 6. 编码原则

Codex 编码时必须遵守：

1. 先实现可运行闭环，再增加复杂功能。
2. 所有脚本必须可单独运行。
3. 所有数据库写入必须有明确状态字段。
4. 所有 LLM 输出必须可结构化校验。
5. 所有发布前必须可预览。
6. 不允许直接覆盖重要知识资产，必须保留草稿或备份。
7. 所有文件输出必须符合目录规范。
8. 所有 Hugo Front Matter 必须符合 `FRONTMATTER_SPEC.md`。
9. 所有编辑决策必须符合 `EDITORIAL_RULES.md`。
10. 不得擅自引入未批准的新框架或数据库。

---

## 7. MVP 成功标准

MVP 被认为成功，需要满足：

1. 连续运行 7 天无严重中断。
2. 每日稳定生成 1 篇日报草稿。
3. 每日最多生成 0-2 篇 A 级候选文章。
4. 重复资讯不会重复入库。
5. A 级内容进入审核队列。
6. Hugo build 成功率达到 95% 以上。
7. 每篇导出内容都有 sources、entities、topics、claims、seo 字段。
8. 没有批量生成低价值独立 URL。
9. 所有运行结果可在 SQLite 或日志中追踪。
